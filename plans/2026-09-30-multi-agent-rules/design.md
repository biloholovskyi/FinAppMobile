# Design — правила для нескольких агентов

Целевое состояние. Принцип: всё, что не зависит от инструмента, живёт в `ai/`, включая порядок работы; инструмент-специфика — тонкие адаптеры в `.claude/` и `.codex/` (+ `.agents/skills/`, каталог, который Codex читает принудительно).

Одинаковый результат двух клиентов — это одинаковые обязательные этапы, ограничения, места артефактов, условия остановки и критерии качества. Буквальное совпадение кода, текста ответа и числа вызовов инструментов критерием не является.

## Структура

```
AGENTS.md                      # общая точка входа (Codex читает сам, Claude — через @AGENTS.md)
CLAUDE.md                      # @AGENTS.md + always-loaded @-импорты + только Claude-специфика
ai/
├── rules/                     # SSoT правил, инструмент-нейтральные
│   ├── INDEX.md               # каталог правил (бывший ai/rules/AGENTS.md)
│   └── common/
│       ├── agent-workflow.md  # общий контракт выполнения
│       └── git-policy.md      # общая git-политика
├── skills/<name>/procedure.md # SSoT процедур скиллов (+ вспомогательные файлы скилла)
└── agents/
    ├── INDEX.md               # роли, классы полномочий, маршрутизация задач
    └── <name>.md              # SSoT ролей агентов
.claude/                       # только Claude Code
├── INDEX.md                   # индекс Claude-слоя (бывший .claude/AGENTS.md)
├── rules/*.md                 # paths-стабы → ai/rules/**
├── skills/<name>/SKILL.md     # адаптер → ai/skills/<name>/procedure.md
├── agents/<name>.md           # адаптер → ai/agents/<name>.md
├── agent-memory/              # локальная оптимизация Claude, не источник обязательных договорённостей
├── reviews/                   # исторические артефакты, не правила
└── settings.json              # permissions, hooks, plugins
.agents/skills/<name>/         # только Codex: адаптеры скиллов
├── SKILL.md
└── agents/openai.yaml         # политика вызова для ручных скиллов
.codex/                        # только Codex
├── README.md                  # Codex-специфика: маппинг тиров, вызов скиллов, trust, ограничения
├── config.toml                # MCP, sandbox/approval
├── agents/<name>.toml         # адаптер → ai/agents/<name>.md
├── rules/git.rules            # forbidden-правила по git-политике
├── hooks/*.mjs                # генераторы JSON-вывода хуков
└── hooks.json
scripts/check-agent-config.mjs # проверка согласованности (переходный и строгий режим)
```

## Общий контракт выполнения — `ai/rules/common/agent-workflow.md`

- Проектный процесс Research → Design → Plan → Implement → Reflect и формат `plans/` приоритетнее процессов подключённых навыков и плагинов (в том числе superpowers в любом клиенте): их spec- и plan-файлы не создаются, brainstorming допустим до плана
- Семантика `np` остаётся в `response-rules.md`; `agent-workflow.md` требует читать `implementation-plans.md` и `response-rules.md` при создании, исполнении и возобновлении плана
- Состояние задачи восстанавливается только из `ai/**` и файлов плана (фаза, evidence, `history.md`); ни одна обязательная договорённость не живёт только в памяти агента или в чате
- Делегирование: таблица «тип задачи → роль» в `ai/agents/INDEX.md`; исполнитель и проверяющий — разные запуски; делегирование по таблице разрешено без отдельного вопроса
- Нет нужного навыка, роли, модели или механизма делегирования: выполнить процедуру из канона напрямую; если обязательное независимое ревью невозможно — явно записать это в evidence фазы, статус «проверено» не присваивать
- Приоритет: правила проекта задают workflow в пределах системных ограничений, прав, sandbox и реально доступных инструментов; файл правил не отменяет sandbox и не создаёт отсутствующую возможность

- Review-артефакты: проверяющая роль не пишет файлы, а возвращает структурированные findings; сохраняет их основной агент. Для задачи с планом — `plans/<plan-folder>/review-<scope>.md`, для задачи без плана — `plans/reviews/YYYY-MM-DD-<slug>-review.md`. Формат отчёта задаёт канон `code-reviewer`. `.claude/reviews/` — история, новые отчёты туда не пишутся
- Проверяющие роли запускают только команды без записи: `rtk yarn tsc --noEmit`, `rtk npx eslint src` (без `--fix`). `rtk yarn lint` содержит `--fix` и остаётся за исполнителем; проверяющий может вместо запуска получить результаты гейтов от исполнителя

В `CLAUDE.md` остаётся только Claude-специфика: снятие встроенной сдержанности Claude на запуск сабагентов по таблице из `ai/agents/INDEX.md` и названия плагинных навыков Claude.

## Контракт QA — `ai/rules/common/post-code-workflow.md`

Устраняет противоречие в текущих правилах: условный tsc в «Required Steps» и безусловный в «One-Line Workflow» того же файла и в процедуре `post-code`.

Последовательность после изменений (остановка на первой ошибке, ошибка не превращается в успешный QA):
1. Изменён код или конфиг сборки (`src/**`, `*.ts`, `*.tsx`, `tsconfig.json`, `eslint.config.js`, `package.json`): `rtk yarn lint`, затем `rtk yarn tsc --noEmit` — всегда, без оценки «есть ли подозрения»
2. Затронуты `AGENTS.md`, `CLAUDE.md`, `ai/**`, `.claude/**`, `.codex/**`, `.agents/**`: `rtk yarn agents:check` (с Phase 08 — `--strict`)
3. Затронуты оба набора — сначала шаг 1, затем шаг 2

Этот порядок одинаков в `post-code-workflow.md`, процедуре `post-code`, `deploy-preflight` (там `agents:check --strict` выполняется всегда) и в каноне `finapp-mobile-expert`.

## Git-политика — `ai/rules/common/git-policy.md`

- Разрешено агенту: `status`, `diff`, `log`, `show`, `ls-files`, `branch --list`/`branch` без аргументов, `rev-parse`
- Запрещено агенту: любые изменения репозитория и ссылок — `commit`, `push`, `add`, `checkout`, `switch`, `branch` с аргументами создания/удаления/переименования, `reset`, `rebase`, `merge`, `revert`, `cherry-pick`, `stash`, `clean`, `restore`, `rm`, `mv`, `tag`
- Коммит-сообщения и все мутации пишет и выполняет пользователь
- Технические запреты клиентов — страховка, а не полное покрытие: глобальные опции (`git -C`), обёртки оболочки и нестандартные вызовы могут их обойти; правило действует независимо от того, сработал ли технический запрет

| Механизм | Claude | Codex |
|------|------|------|
| Запрет мутаций | `permissions.deny` для Bash и PowerShell, прямой вызов и `rtk`; полный список подкоманд, включая `switch` | `prefix_rule(..., decision = "forbidden")` для `git` и `rtk git` |
| Чтение | `permissions.allow` только read-only подкоманд; `rtk git branch:*` сужается до списка | правил `allow` нет — чтение работает в sandbox |
| Проверка | ручные пробы решений `permissions` без выполнения мутаций | `codex execpolicy check` для прямого вызова, `rtk`, `git -C`, `bash -lc` |

Правила `allow` для `rtk yarn`/`rtk npx` в Codex не заводятся: `allow` означает запуск вне sandbox без вопроса.

## Точки входа

`AGENTS.md` (до 150 строк, до 12 KiB):
- Стек и закреплённые версии кратко; критические ограничения; команды
- «Read first»: `response-rules.md`, `agent-workflow.md`, `git-policy.md`, `patterns.md`, `token-economy.md`; `implementation-plans.md` — при планировании и исполнении плана
- Таблица «задача → файл правил» (поглощает `core-rules.md`)
- «Agent tooling»: канон в `ai/skills`, `ai/agents`; навигационные ссылки `.claude/INDEX.md`, `.codex/README.md`
- Запрещённое содержание: синтаксис вызова конкретного клиента, имена моделей, `@`-импорты, правила, понятные только одному клиенту

`CLAUDE.md` (до 80 строк): `@AGENTS.md` первой строкой; @-импорты `response-rules`, `agent-workflow`, `git-policy`, `patterns`, `token-economy`, `implementation-plans`; снятие сдержанности на сабагенты; маппинг тиров на алиасы Claude; ссылка на `.claude/INDEX.md`.

Асимметрия: Claude получает «Read first» в контекст сразу, Codex читает по указанию. Проверяется сценарием приёмки.

Родительский `C:\Projects\FinApp\CLAUDE.md` загружается Claude и не редактируется; мобильный проект не зависит от его содержания — всё обязательное есть в собственных файлах.

## Скиллы

Канон: `ai/skills/<name>/procedure.md` — без frontmatter, `$ARGUMENTS`, имён моделей. Аргумент описан словами. Вспомогательные файлы рядом с процедурой; пути в процедурах — от корня репозитория.

Классы скиллов и политика вызова (одинаковая в обоих клиентах):

| Класс | Скиллы | Неявный вызов | Claude | Codex |
|------|------|------|------|------|
| Проверки | `lint`, `typecheck`, `post-code`, `audit-plan`, `audit-security`, `review-react-perf`, `deploy-preflight`, `eas-status` | да | по умолчанию | по умолчанию |
| Локальная подготовка | `start-task`, `implement-plan-step`, `commit`, `ui-ux-pro-max` | да | по умолчанию | по умолчанию |
| Внешние действия | `eas-build`, `eas-submit` | нет | `disable-model-invocation: true` | `allow_implicit_invocation: false` |

Обнаружение скилла и авторизация действия разделены: даже вызванный явно `eas-build`/`eas-submit` выполняет внешнее действие только после явного подтверждения в чате, как сейчас в процедуре.

| Поле | Claude `.claude/skills/<name>/SKILL.md` | Codex `.agents/skills/<name>/SKILL.md` |
|------|------|------|
| `name`, `description` | как в каноне, декодированные значения совпадают | то же |
| Модель | `model:` по тиру | нет |
| Аргументы | `Arguments: $ARGUMENTS` | «аргументы — из сообщения пользователя» |
| Тело | «Read and follow `ai/skills/<name>/procedure.md`» | то же, одноимённый канон |

## Агенты

Канон `ai/agents/<name>.md`: роль, «When to use», нейтральная матрица полномочий, маршрутизация правил, формат отчёта и handoff.

Матрица полномочий в каноне: чтение, поиск, проверочные команды, правки файлов, сеть, внешние действия — для каждой роли «да/нет». Адаптер указывает, что ограничено технически, а что только инструкцией.

Матрица сверена с исходными ролями и сохраняет их поведение; единственное намеренное изменение — `code-reviewer` (см. ниже).

| Роль | Правки файлов | Команды | Внешние действия | Codex sandbox |
|------|------|------|------|------|
| `codebase-researcher`, `plan-auditor`, `react-performance-reviewer`, `full-package-auditor` | нет | нет — только чтение и поиск; проверочные команды предлагаются основному агенту | нет | `read-only` |
| `code-reviewer` | нет | только без записи (`tsc --noEmit`, `eslint` без `--fix`) | нет | `read-only` |
| `dependency-analyst` | нет | диагностика без записи: `expo install --check`, `yarn why`, `yarn outdated`, `yarn audit`; установка и обновление — только предложение команды | нет | `read-only` |
| `command-runner` | нет прямых правок; изменения только как побочный эффект запрошенных скриптов (`lint --fix`, `api:generate`) | да, `rtk`-скрипты из `tooling.md` | нет | `workspace-write` |
| `finapp-mobile-expert`, `screen-designer` | да | да | нет | `workspace-write` |
| `eas-deployer` | да | да | только по явному запросу | `workspace-write` |

Для ролей с памятью в Claude (`memory: project`) запись в собственный `.claude/agent-memory/<name>/` — Claude-исключение из «правки — нет»; в Codex памяти нет.

Намеренное изменение `code-reviewer`: сейчас без ограничения `tools` и сам пишет отчёт в `.claude/reviews/`. Целевое: `tools: Read, Glob, Grep, Bash`, отчёт возвращается основному агенту (контракт review-артефактов выше). `description` уже обещает read-only и не меняется. Сетевой доступ `dependency-analyst` в Codex read-only sandbox проверяется в Phase 05; при отсутствии сети команды, требующие реестра, выполняет основной агент.

| Поле | Claude `.claude/agents/<name>.md` | Codex `.codex/agents/<name>.toml` |
|------|------|------|
| Идентификация | `name`, `description`, `<example>`-блоки | `name`, `description` |
| Инструкции | «Read `ai/agents/<name>.md` first» + путь памяти при `memory: project` | `developer_instructions` с тем же указателем |
| Техническое ограничение | `tools` | `sandbox_mode = "read-only"` для ролей без правок; чтение через shell допускается только read-only командами — инструкцией |
| Модель | `model` по тиру | `model`, `model_reasoning_effort` по тиру и доступности из Phase 01 |

## Хуки

Хук — только напоминание; прохождение QA подтверждается запуском гейтов и записью результата в evidence, в том числе при отключённых хуках. Хуки не изменяют проект и не выполняют внешних действий.

| Событие | Claude | Codex |
|------|------|------|
| После правки | `PostToolUse`, matcher `Write\|Edit\|MultiEdit`, echo | `PostToolUse`, matcher `apply_patch\|Edit\|Write`, скрипт `.codex/hooks/post-edit.mjs` → JSON `hookSpecificOutput.additionalContext` |
| Конец сессии | `Stop`, echo | `Stop`, скрипт `.codex/hooks/stop.mjs` → валидный JSON без продолжения, текст в `systemMessage` |

Разрешение пути скрипта: hook-команды Codex запускаются с cwd сессии, поэтому путь к скрипту вычисляется от git-root до запуска Node (`git rev-parse --show-toplevel`), без абсолютных путей машины разработчика и с кавычками, выдерживающими пробел в пути. Конкретная форма команды выбирается под оболочку, которой Codex исполняет хуки на Windows (фиксируется в Phase 01). Префикс `rtk` к hook-командам не применяется: это конфигурация, исполняемая клиентом, а не shell-команда агента — исключение записывается в `.codex/README.md`.

## Проверка согласованности — `scripts/check-agent-config.mjs`

- Переходный режим (по умолчанию до Phase 08): проверяет только существующие пары и пути, которые должны существовать на текущей фазе
- Строгий режим `--strict` (обязательный с Phase 08):
  - ожидаемый набор: 14 скиллов, 10 ролей, `AGENTS.md`, `CLAUDE.md`, `.claude/INDEX.md`, `.codex/README.md`, `.codex/config.toml`
  - пары канон ↔ адаптеры в обе стороны; адаптер ссылается именно на одноимённый канон
  - совпадение декодированных `name`/`description` (YAML и TOML), политика вызова по классам
  - существование путей из обратных кавычек, голых `@`-импортов, Markdown-ссылок и путей в конфигах
  - `AGENTS.md` до 12 KiB и 150 строк
- Парсер без зависимостей поддерживает зафиксированное подмножество (однострочные скаляры, строки в кавычках, многострочный `description` через `>`/`|`); неподдерживаемый синтаксис — ошибка, не пропуск
- Точки запуска — по контракту QA: шаг 2 процедуры `post-code` и всегда в `deploy-preflight`
- Repo-root ссылки вида `plans/...`, `ai/...` разрешаются от корня репозитория — это принятая схема проекта
- Отрицательные пробы: только от положительного baseline, на котором проверяемый режим возвращает 0; один дефект за пробу; проверяется код 1 и сообщение именно о внесённом дефекте; после восстановления — снова 0. Переходный режим — на синтетической копии в scratch в Phase 03, строгий — на копии полного дерева в Phase 08

## Статусы runtime-проверок

- Phase 04–05: критерий `done` — перенос файлов, статические проверки и runtime в Claude; наблюдения в Codex — предварительные, не блокируют `done`, записываются в evidence
- Phase 06: runtime в Codex обязателен — это результат фазы; недоступный клиент блокирует `done`
- Phase 07: runtime загрузки точек входа в обоих клиентах обязателен
- Окончательные доказательства паритета — только Phase 09, после появления общей точки входа

## Модели

`ai/rules/common/ai-models.md` — только тиры FAST / BALANCED / DEEP / LONG_CONTEXT и назначения тиров. Маппинг — в `CLAUDE.md` и `.codex/README.md`. Запись тира в плане не переключает основную модель автоматически: переключение — действие пользователя или параметр адаптера сабагента.

## Владение документацией

- `ai/**` — SSoT правил, процедур, ролей и порядка работы
- `AGENTS.md` — общая точка входа, ссылается на `ai/**`
- `CLAUDE.md` + `.claude/**` и `.codex/**` + `.agents/**` — адаптеры; ссылаются на `ai/**` и `AGENTS.md`
- `ai/**` не ссылается на клиентские слои, кроме раздела Agent Layout в `tooling.md`
- Исключения из правила «в `.claude/**` только метаданные и указатели»: `agent-memory/`, `reviews/` (история), `settings.json`
- Новые review-отчёты — в `plans/**` по контракту review-артефактов
