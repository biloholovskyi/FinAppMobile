## HIGH

### R2-H1. Новая матрица полномочий расходится с сохраняемыми ролями

Места: `plans/2026-09-30-multi-agent-rules/design.md:114–115`; `plans/2026-09-30-multi-agent-rules/phase-05-agents.md:23–30,42`.

В новой матрице `dependency-analyst` включён в группу с правками файлов. Но исходный `.claude/agents/dependency-analyst.md:9,39` прямо задаёт read-only и запрет менять файлы; description обещает рекомендации без изменений. Phase 05 одновременно требует сохранить description, инструменты и поведение Claude-агентов. При буквальном исполнении получится противоречивый канон, а Codex-адаптер этого аналитика не получит read-only sandbox, поскольку он назначается только ролям «без правок».

Вторая несогласованность: `full-package-auditor` в матрице получает выполнение проверочных команд, хотя исходный frontmatter допускает только Read/Glob/Grep. Тело роли предлагает команды основному агенту, а не выполняет их само (`.claude/agents/full-package-auditor.md:4,50`). Сохранение frontmatter оставит Claude без возможности выполнить предписанный общий процесс.

**Исправление:** сверить матрицу с каждой исходной ролью. Для сохранения поведения у `dependency-analyst` оставить «правки — нет», разрешённые диагностические команды — да, и назначить Codex read-only. У `full-package-auditor` оставить проверочные команды за основным агентом/command-runner. Если расширение роли намеренное, обозначить его отдельным изменением поведения и согласованно поменять оба адаптера, description и критерий сохранения поведения.

Дополнительно определить допустимые команды для проверяющих: `package.json:11` задаёт `lint` как `eslint src --fix`. Поэтому `rtk yarn lint` нельзя считать проверкой без записи только из-за названия. Reviewer либо получает результаты от исполнителя, либо использует вариант без исправлений; автоматические исправления остаются у исполнителя.

**Приёмка:** матрица и оба адаптера не противоречат друг другу; dependency-analyst не меняет package/lock/source-файлы; full-package-auditor не пытается использовать отсутствующий инструмент; проверяющий не запускает auto-fix в исходниках.

### R2-H2. Обязательный typecheck в плане не обеспечивается переносимой процедурой

Места: `plans/2026-09-30-multi-agent-rules/phase-04-skills.md:13,19,43`; сценарий 7 Phase 09.

План требует одинаковый post-code: lint, затем tsc. Однако исходный `.claude/skills/post-code/SKILL.md:19` разрешает запускать TypeScript check только при подозрении на ошибки. Та же условность находится в `ai/rules/common/post-code-workflow.md:8,20`. Этот файл отсутствует в явном scope нейтрализации Phase 02 и синхронизации Phase 08.

Перенос тела процедуры с добавлением `agents:check` сохранит субъективную развилку: один клиент запустит tsc, другой сочтёт его ненужным. Более того, `finapp-mobile-expert` по Phase 05 будет читать именно старое условное правило. Даже исправление одной процедуры не устранит расхождение.

**Исправление:** явно выбрать общий контракт QA. Для уже заявленных критериев плана — обязательные lint → tsc после соответствующих изменений кода, затем `agents:check` при заданных условиях. Внести согласованное изменение в будущую процедуру post-code и `ai/rules/common/post-code-workflow.md`, добавить последний в scope нужной фазы. Отметить это как устранение противоречия в правилах, а не только замену формулировок. Точное место `agents:check` в последовательности тоже зафиксировать.

**Приёмка:** после успешного lint оба клиента запускают tsc без оценки «есть ли подозрения»; при ошибке не отмечают QA успешным. Прямое следование `post-code-workflow.md` и вызов навыка дают одну последовательность.

## MEDIUM

### R2-M1. Пути запуска хуков зависят от cwd и ломаются из подкаталога

Места: `plans/2026-09-30-multi-agent-rules/design.md:131–132`; `plans/2026-09-30-multi-agent-rules/phase-06-codex-config.md:16`.

Предписаны команды `node .codex/hooks/post-edit.mjs` и `node .codex/hooks/stop.mjs`. Документация Codex указывает, что hook-команды запускаются с cwd сессии, и отдельно рекомендует разрешать путь от git-root. При сессии из `src/` Node будет искать `src/.codex/hooks/...`, а не файл в корне проекта. Источник: [официальная документация Codex Hooks, примечания к конфигурации команд](https://learn.chatgpt.com/docs/hooks).

Запуск из подкаталога уже входит в scope Phase 01/07 и сценарий 5. Текущая Phase 06 не требует проверить хуки в этом режиме, поэтому основная проверка может пройти, оставив ошибку.

**Исправление:** определить путь скрипта относительно корня репозитория до запуска Node. Реализация должна учитывать фактическую оболочку Windows/Git Bash и корректное quoting; не подставлять абсолютный путь машины разработчика. При необходимости использовать отдельную поддерживаемую Windows-команду. Сохранить принятое правило RTK для shell-команд либо явно описать обоснованное исключение для hook runner.

**Приёмка:** PostToolUse и Stop успешно работают в свежих сессиях из корня и `src/`, а также при пробеле в пути временной копии. Проверяются фактическая доставка напоминания и отсутствие ошибок запуска, а не только валидность JSON скрипта.

### R2-M2. Не определён общий путь и владелец сохранения новых review-отчётов

Места: `plans/2026-09-30-multi-agent-rules/design.md`, разделы «Агенты» и «Владение документацией»; `plans/2026-09-30-multi-agent-rules/phase-05-agents.md`.

Исходный `.claude/agents/code-reviewer.md:45–48` требует сохранить отчёт в абсолютный путь `.claude/reviews/<feature-name>-review.md`. Новый дизайн объявляет `.claude/reviews/` историческими артефактами, запрещает клиентские пути в каноне и одновременно переводит reviewer в режим без правок файлов. Phase 05 отдельно разбирает перенос памяти, но не разбирает это требование к отчётам.

Если удалить указание, можно потерять обязательный артефакт. Если оставить в Claude-адаптере — места результата будут различаться. Если просто заменить путь в каноне — Codex reviewer в read-only не сможет выполнить требование записи.

**Исправление:** выбрать одно общее место для новых отчётов и указать автора записи. Рекомендуемый вариант: reviewer возвращает структурированные findings; основной агент сохраняет их в выбранный файл плана, а для задачи без плана — в отдельный согласованный общий каталог. Старые `.claude/reviews/` остаются историей. Не поручать read-only reviewer запись отчёта.

**Приёмка:** один и тот же review-запрос в обоих клиентах создаёт одинаковый тип артефакта в общем месте; дочерний reviewer не пишет файлы, а основной агент не теряет его вывод. Проверить также задачу без implementation plan.

### R2-M3. Негативные пробы checker не отделены от заведомо неполного дерева

Место: `plans/2026-09-30-multi-agent-rules/phase-03-drift-check.md:35–43`.

В Phase 03 строгий режим уже обязан завершаться с ошибкой из-за отсутствия файлов будущих фаз. Затем успехом отрицательных проб считается exit code 1. Если временная копия взята из того же неполного дерева, этот код останется 1 даже у checker, который вообще не обнаруживает внесённый дефект. Проба удаления всего комплекта навыка особенно уязвима: целевой комплект на этой фазе ещё не создан.

**Исправление:** для временных проб сначала подготовить минимальный полный валидный комплект, на котором `--strict` возвращает 0. Затем вносить по одному дефекту и проверять не только exit code 1, но и диагностику именно внесённой ошибки. После восстановления исходного комплекта снова ожидать 0. Альтернатива — перенести полные строгие отрицательные пробы в Phase 08, сохранив в Phase 03 проверки переходного режима.

Постоянные fixtures, тестовый фреймворк и CI для этого не нужны; выбранное в ответе ограничение scope сохраняется.

**Приёмка:** в evidence есть положительный baseline и результат каждой отдельной отрицательной пробы с конкретным сообщением; отсутствие файлов будущих фаз не считается доказательством обнаружения другого дефекта.

## Небольшое уточнение статусов

В Phase 04 разрешена запись «Codex не проверен», но Acceptance Criteria требуют, чтобы оба клиента выполняли post-code одинаково. Выбрать однозначную трактовку: либо эта runtime-проверка обязательна для `done`, либо переносится в Phase 09 как явно обозначенная незавершённая приёмка при завершённом переносе файлов. Аналогично отделить предварительные runtime-наблюдения от окончательных доказательств после Phase 07, когда появится общая точка входа.
