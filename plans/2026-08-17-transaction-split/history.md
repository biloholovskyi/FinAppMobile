# History — Разделение платежа

Handoff-заметки по фазам. Запись добавляется в момент перевода фазы в статус `done`.

## Phase 01 — Состояние разделения (17.08.2026)

- Хук `useTransactionSplit` держит активность разделения, базовую сумму и поля нового платежа; расчёты идут в целых копейках через `TRANSACTION_SPLIT_PRECISION_FACTOR`
- Состояние новой части вынесено в под-хук `useSplitPart`, чтобы основной хук уложился в лимит 50 строк (44)
- Хук не владеет полем «Сумма»: отдаёт `remainderStr`, экран сам решает, что показывать — это убирает необходимость откатывать значение при выключении
- Тексты валидации и сообщение о частичном сохранении заведены заранее в `TRANSACTION_SPLIT_MESSAGES` — фаза 03 их только потребляет
- Известное ограничение: база, зафиксированная из пустого поля «Сумма», равна нулю и схлопывает ввод новой части в `0` — валидация фазы 03 обязана это отсечь
- `parseAmountInput` не подошёл: он трактует ноль и пустую строку как ошибку, а промежуточный ввод новой части должен быть нулём — в хуке своя целочисленная копеечная математика, вынос в `shared/utils/currency` отложен до аудита
- Гейты зелёные: lint без ошибок, tsc без ошибок
- `rtk` в среде отсутствует, команды выполнялись без префикса

## Phase 02 — UI разделения (17.08.2026)

- Карточка нового платежа переиспользует `FormRow` и `CategoryPickerModal`; собственные модалки живут в co-located хуке `useSplitPaymentCard`, поэтому экран не раздувается
- Поле «Сумма» стало компонентом `AmountField` с режимом read-only и подписью-хинтом; экран показывает `amountValue`, а не `form.amountStr`
- Чтобы уложить экран в лимит 150 строк (было 193, стало 147), из него вынесены `TypeSegment`, `AmountField`, `DescriptionRow`, `ActionButtons`
- Сброс разделения при уходе с типа «Расход» сделан обёрткой `changeType` в `useEditTransactionScreen`
- Инлайн `style` для типографики оставлен как есть — это существующий паттерн экрана, унификация отложена до аудита
- `useEditTransactionScreen` вырос до ~105 строк при лимите 50 — долг зафиксирован для фазы 04
- Сохранение пока однозапросное: разделение в него не включено, это работа фазы 03
- Гейты зелёные: lint без ошибок, tsc без ошибок

## Phase 03 — Сохранение двумя запросами (17.08.2026)

- `handleSave` принимает второй необязательный payload; при его наличии выполняет PATCH исходной транзакции, затем POST новой, и только после обоих успехов инвалидирует кэш и закрывает экран
- Новый платёж собирается спредом основного payload — «копируется всё, кроме категории и суммы» видно прямо в коде
- Признак `isSourceUpdated` защищает от повторного вычитания: после частичного успеха повторное сохранение делает только создание
- Внутри одного вызова `handleSave` признак дублируется локальной переменной — состояние React в пределах вызова не обновляется, иначе сообщение об ошибке второго запроса было бы неверным
- Суммы отправляются в единицах валюты, а не в копейках: так устроен существующий контракт экрана, разделение ему следует
- Долг по длине хуков вырос: `useEditTransactionScreen` — 138 строк, `useEditTransactionActions` — 79 при лимите 50
- Гейты зелёные: lint без ошибок, tsc без ошибок

## Phase 05 — Reflect (17.08.2026)

- Расхождения с дизайном сводятся к структуре файлов, а не к поведению: лимиты компонентов и хуков потребовали четырёх дополнительных модулей и четырёх подкомпонентов экрана
- Главный остаточный риск — неатомарность двух запросов: закрытие экрана после частичного успеха оставит исходную транзакцию уменьшенной без парного платежа
- Второй риск — нетипизированные generated-DTO: ошибка в имени поля payload не ловится компилятором
- Реализация проверена только статическими гейтами; ручной прогон сценариев разделения остаётся за пользователем
